## Findings

### 1. medium – Daily kernel preparation can fill a small persistence partition

`src/frfw/kernel_update.py`, `prepare()` (the `apt-get install` of
`linux-image-<v>`). `fr-kernel-prepare.timer` runs daily and
`update.kernel_updates` is on by default. A Debian kernel package
installs about 400 MB of modules into the persistent root; its initrd and
the staged copy add about 100 MB more. `frfw.persistence` creates
persistence partitions down to 256 MiB (`MIN_BYTES`), and nothing checks
the free space before the install.

**Scenario:** a router on a small stick (or with the minimum partition)
gets the first Debian kernel update: dpkg fills the partition and fails
half-way. From then on `config.yaml` can't be saved, the audit log and
the journal stop, and dpkg is left with a half-configured package that
the next unattended-upgrades run trips over.

**Fix:** before installing, read the package's `Installed-Size` (`apt-cache
show`) and refuse unless the persistence filesystem keeps the package,
an initrd, a staged copy and a fixed reserve free; say so in the
kernel card's last check.

### 2. medium – `verify-medium.py` follows symlinks inside the untrusted medium

`src/frfw/integrity.py`, `OverlayView.read()`, and
`scripts/verify-medium.py`, `mounted_medium()`. The tool runs as root on
the admin's other computer against a stick that may have been tampered
with. `read()` refuses a final component that is a symlink, but
`Path.exists()` / `read_bytes()` resolve every intermediate component, so
`rw/usr` → `/` on the persistence layer makes it read the *verifying
computer's* `/usr/local/...`. The filesystems are mounted with `ro` only
(devices, setuid and symlinks honoured).

**Scenario:** a crafted persistence layer points a directory at
`/dev/zero`-like or huge files of the verifying machine (memory and
time exhaustion as root), or at that machine's own files, which are then
hashed and compared. It can't forge a pass -- the release is verified
with the checkout's keys and an implant still has to sit in a real
directory for the router to run it -- but a check meant for untrusted
media shouldn't follow the medium's links out of it.

**Fix:** mount with `nodev,nosuid,noexec,nosymfollow`, and have
`OverlayView` refuse any path whose components, below the layer root,
include a symlink (checked with `lstat`, so it holds without
`nosymfollow` too).

### 3. medium – The integrity checks cover FR_OS's own files only

`src/frfw/integrity.py`, `scripts/verify-medium.py`, ARCHITECTURE
"Detecting persistence". Both the router's check and the offline one
compare FR_OS's package, units, scripts and XDP program with the signed
release. A root attacker who persists through anything else in the
persistence layer -- a systemd unit or drop-in, `sitecustomize.py` in
the system Python, a cron entry, `/root/.ssh/authorized_keys`, a patched
Debian binary -- is not reported by either.

**Scenario:** an attacker with root drops
`/etc/systemd/system/multi-user.target.wants/x.service`; both checks say
"every file matches the signed release", and an admin reads that as "the
router is clean".

**Fix:** say plainly, on the System screen, in `firewall-cli integrity`
and verify-medium's output, that the check is about FR_OS's own files.
Then (a follow-up) let verify-medium list every file the persistence
layer adds or changes outside an expected set (config, state, logs),
and check Debian's own files against the package archive's signed
indexes -- the upper layer is the only place a live router's changes can
be, which makes that list finite.

### 4. low – The Update screen hashes the staged kernel on every page load

`src/frfw/kernel_update.py`, `overview()` → `kernel_boot.status()` →
`files_intact()`. Each view of `/update` makes the update-helper read the
staged kernel and initrd (50-100 MB) to hash them.

**Scenario:** on a router booting from a USB 2 stick, every Update page
load takes seconds of I/O; an admin who refreshes it competes with the
router's own disk use.

**Fix:** the page doesn't need the hash check (GRUB does it at every
boot, and `firewall-cli kernel status` still runs it): skip it in
`overview()`.

### 5. low – A second medium can supply the staged kernel or the persistence layer

`installer/live-build/config/includes.binary/boot/grub/grub.cfg`
(`search --file /fr_os-boot/grubenv`); live-boot's own search for a
filesystem labelled `persistence`. GRUB takes the first filesystem that
has `fr_os-boot/grubenv`, and live-boot the first labelled
`persistence`, on any attached disk.

**Scenario:** someone with physical access plugs in a stick with their
own `fr_os-boot/` (or `persistence` filesystem) and power-cycles the
router: their kernel (or their files in the root) boots, even where the
firmware only boots the FR_OS stick.

**Status suggestion:** accepted -- physical access to an unencrypted
boot medium is already full control (the stick itself can be rewritten),
and `verify-medium.py` is the answer to tampering. Worth a sentence in
SECURITY.md's scope.

### 6. low – One staged slot

`src/frfw/kernel_boot.py`, `stage()`. Staging kernel N+1 replaces a
confirmed kernel N; if N+1 fails its trial the router boots the image's
kernel, which may be older than N.

**Status suggestion:** accepted, documented in ARCHITECTURE; the image's
kernel is the one known-good kernel the medium carries.

### 7. low – The Debian download path has only run against a fake apt

`src/frfw/kernel_update.py`, `prepare()` with no `--version`. The boot
test prepares the running kernel (no newer one exists while the image is
built with the newest), so `apt-get install linux-image-<v>` and its
maintainer scripts on a live router have not run for real.

**Status suggestion:** accepted -- a failure there leaves the kernel not
ready, says so on the Update screen, and nothing boots; the first real
Debian kernel update exercises it. A reproducible test could install a
Debian kernel package from a local repository in the boot test.

## Checked and found sound

- Both helpers: per-uid roles from `SO_PEERCRED`; the update-helper's
  new kernel commands are full-role only and refuse a sensor peer
  (tested over the real socket); `kernel_try` stages only what root
  recorded in a 0600 state file, never a path from the request.
- The GRUB state machine writes the new state before booting a staged
  kernel and boots it only if the write worked; loads only its two
  variables; checks the files' hashes; falls back on every failure the
  boot test produced (panic, failed health check, broken initrd).
- `fr-kernel-confirm` never reboots on its own bugs (one explicit
  `systemctl reboot` for a failed trial); its sandbox (CAP_NET_ADMIN,
  localhost only) held in the boot test.
- The webUI escapes the XDP log's attacker-controlled names
  (`xdp.js` `escapeHtml`, CSP `script-src 'self'`); the only `|safe`
  outputs are server-generated QR SVGs.
- `/metrics` compares the token digest in constant time.
- The kernel update's initrd is edited, not unpacked (no setuid or
  device files recreated), and must keep live-boot.
