## High findings

### FR-001 — Root-level updates install unpinned PyPI dependencies

`pyproject.toml` specifies dependencies using minimum versions rather than exact versions or hashes. The update path in `src/frfw/update.py` runs pip as root with `--break-system-packages --no-cache-dir`.

A cryptographically valid FR_OS release can therefore cause installation of whatever dependency versions are resolved from PyPI at update time.

**Suggested fix:** use a reproducible lock file with exact versions and hashes; install with `--require-hashes`, ideally from a controlled artifact repository/bundle.

### FR-002 — Security enforcement state can silently disappear during a successful firewall apply

The generated nftables ruleset begins with `flush ruleset`. FR_OS snapshots brute-force bans, IDS quarantines, ZTNA sessions and IoT isolation before reload, but restoration errors are best-effort and can be swallowed.

**Failure scenario:** an existing quarantine is flushed; restoration fails; apply still succeeds; the previously blocked host becomes allowed.

**Suggested fix:** make restoration failure fail the apply for security enforcement sets, retry restoration, expose exact failed state, and make runtime-state restoration transactional where possible.

### FR-003 — Debian security repository explicitly disabled

`installer/live-build/auto/config:160` contains `--security false`.

**Suggested fix:** enable the appropriate Debian security repository and establish a defined OS-level security update policy.

## Medium findings

### FR-004 — Non-transactional cross-subsystem apply

`src/frfw/provision.py` applies firewall, forwarding, WireGuard, addresses, DHCP, DNS, XDP and management state sequentially without cross-subsystem rollback.

**Suggested fix:** prevalidate, snapshot, stage, verify and roll back where possible. At minimum, management and firewall changes need recovery semantics.

### FR-005 — XDP parser does not enforce protocol-declared boundaries

`bpf/xdp_sni_filter.c` checks packet accesses against `data_end`, but parsing is not consistently constrained by IPv4 `tot_len` or TLS record length.

**Suggested fix:** establish strict `ip_end` and TLS-record boundaries and reject malformed length relationships.

### FR-006 — Broad journal access

`fr-webui.service` and the AI IDS service receive `systemd-journal` supplementary-group access.

**Suggested fix:** expose only the required log stream through a dedicated file, socket, journal namespace or service.

### FR-007 — Unauthenticated metrics endpoint

`src/frfw/webui/routes/metrics.py` does not require login, and `metrics_token_ok()` accepts requests when no token is configured.

The metrics expose security/system telemetry including quarantine counts, ZTNA sessions, interface statistics, application information and XDP state.

**Suggested fix:** require authentication/token by default or bind metrics to a dedicated trusted management interface.

### FR-008 — ZTNA is source-IP authorization

ZTNA authorizes a source IPv4 address into an nftables set.

**Suggested fix:** use per-client cryptographic identity such as WireGuard, mTLS or signed short-lived credentials if device/user-level authorization is intended. Otherwise document it as source-network authorization.

## Low findings

### FR-009 — No trusted release key in reviewed commit

The update verifier requires trusted Ed25519 public keys, but the reviewed `src/frfw/release_keys/` contains no public-key PEM. Signature verification therefore fails closed.

**Suggested fix:** include the intended production public key and test a signed release end-to-end.

### FR-010 — First boot relies on NIC enumeration order

`scripts/fr-first-boot.sh` assigns the first detected NIC as WAN and second as LAN.

**Suggested fix:** use explicit port mapping, link-state/interactive identification or administrator confirmation.

### FR-011 — No explicit CSRF tokens

No explicit synchronizer/double-submit CSRF token mechanism was found in state-changing WebUI routes. Current protection relies substantially on cookie/browser SameSite semantics.

**Suggested fix:** add explicit CSRF protection, especially for Apply, rollback, account, MFA, update and management-exposure operations.

### FR-012 — Missing regression coverage

Dedicated tests were not found for failed runtime-state restoration, partial cross-subsystem apply, malformed IPv4/TLS parser boundaries, unauthenticated metrics, CSRF, dependency hash/lock enforcement and production release trust-anchor presence.

**Suggested fix:** add regression tests for these invariants.

## Positive security observations

The review did not identify a confirmed authentication bypass or direct arbitrary-command injection in the reviewed paths.

Strong controls observed include scrypt password hashing, login throttling, TOTP/WebAuthn MFA, WebAuthn validation, session invalidation after password changes, admin/viewer RBAC, last-admin protection, Unix-socket peer credential checks, separate privileged helpers, safe YAML loading, extensive input validation, nft syntax validation, firewall default-drop input/forward policy, signed-release verification architecture, checksum verification, archive path-traversal checking, restrictive service sandboxing and random first-boot passwords.
