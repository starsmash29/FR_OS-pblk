# 2. Findings

## FR-NEW-001 — Release workflow does not cryptographically bind the build to the release tag

**Severity:** High  
**Category:** Supply-chain security / release integrity  
**File:** `.github/workflows/build-installer.yml`

### Description

The release workflow accepts a `release_tag` through `workflow_dispatch` and checks that the supplied release tag corresponds to the expected application version.

However, the workflow does not establish that the commit actually checked out by the workflow is the exact commit pointed to by that release tag.

The build archive is subsequently generated from the checked-out `HEAD`.

In other words, the workflow verifies a relationship similar to:

`release tag name == application version`

but does not verify:

`GITHUB_SHA == commit pointed to by release tag`

### Failure scenario

Consider:

- `v0.4.0` points to trusted commit A.
- A different branch contains malicious or unintended code but still reports version `0.4.0`.
- The workflow is manually dispatched against that branch while supplying `v0.4.0`.
- The version check succeeds.
- The archive is created from that branch's `HEAD`.
- The resulting installer/release can therefore contain code that is not the code represented by the release tag.

If the resulting artifact is subsequently signed with the FR OS release key, the provenance problem becomes a release-integrity problem.

### Recommendation

Require the release workflow to resolve the supplied tag to an immutable commit and compare it with the actual checkout SHA.

Conceptually:

```text
tag_sha = git rev-list -n 1 "$RELEASE_TAG"
require GITHUB_SHA == tag_sha
```

Preferably:

1. Permit production release builds only from immutable release tags.
2. Resolve the tag to its commit SHA.
3. Explicitly checkout that SHA.
4. Verify the resulting `HEAD` is exactly the expected SHA.
5. Generate the release archive only after this verification.
6. Record the commit SHA in release metadata.

This should be treated as a release-security invariant rather than merely a workflow convenience.

## FR-NEW-002 — Release signing key is too directly exposed to mutable CI workflow execution

**Severity:** High  
**Category:** Supply-chain security / key management  
**File:** `.github/workflows/build-installer.yml`

### Description

The release workflow exposes the private FR OS release-signing key through the CI job environment and gives the workflow write capability needed to publish release artifacts.

The signing key is a root of trust for the FR OS update mechanism. Possession of that key can allow an attacker to create a malicious update that the router considers an authentic FR OS release.

The workflow also relies on GitHub Actions referenced by mutable version tags such as `actions/checkout@v4` and `actions/upload-artifact@v4`, rather than immutable commit SHAs.

### Failure scenario

If an attacker gains the ability to execute or influence the release workflow, or compromises a mutable action used by the workflow, the attacker may be able to access the signing key from the job environment.

The attacker could then:

1. Sign a malicious FR OS release.
2. Publish or otherwise distribute the artifact.
3. Have FR OS clients accept the malicious artifact because its cryptographic signature is valid.

This is a substantially more serious failure mode than an ordinary CI compromise because it crosses the boundary into the update trust root.

### Recommendation

Use a layered release-security design:

1. Put production signing in a protected GitHub Environment.
2. Require explicit reviewers for production signing.
3. Separate build and signing jobs.
4. Give the build job no access to the private signing key.
5. Minimize `GITHUB_TOKEN` permissions.
6. Pin security-sensitive third-party Actions to full immutable commit SHAs.
7. Restrict who may manually dispatch production release workflows.
8. Preferably move the private signing operation outside the GitHub runner entirely.

The strongest long-term design is:

`GitHub build -> artifact digest -> protected signing service/HSM -> signed release`

with OIDC/workload identity used to authorize the CI job to request a signature without exposing the private key itself.

The release key should be treated as an infrastructure root of trust, not merely another CI secret.

## FR-NEW-003 — Kernel trial health check is too shallow

**Severity:** Medium  
**Category:** Correctness / availability / rollback safety  
**Area:** Kernel update/trial mechanism, including `src/frfw/kernel_update.py`

### Description

The new kernel update architecture is a strong improvement: kernel installation, initrd generation, staging, trial boot, health confirmation and fallback are all conceptually appropriate.

The remaining weakness is the definition of a successful trial.

A system can boot successfully and still be unusable as a router.

A kernel health check that primarily proves:

- kernel boots
- systemd starts
- filesystem is usable
- basic FR OS services are alive

does not prove that the network dataplane/control plane is healthy.

### Failure scenario

A new kernel may boot successfully while introducing a regression affecting:

- WAN NIC driver
- LAN NIC driver
- VLAN functionality
- forwarding
- nftables
- Kea DHCP
- DNS
- WireGuard
- XDP
- default route
- management interface/listener

If the health check passes before detecting one of these failures, the new kernel can be promoted instead of automatically falling back.

### Recommendation

Define a kernel trial health contract based on the actual configured FR OS deployment.

At minimum, where configured, validate:

- expected kernel identity/version
- persistent filesystem availability
- expected NICs exist
- WAN interface state
- LAN interface state
- configured VLAN interfaces
- IPv4/IPv6 forwarding state
- nftables ruleset successfully loaded
- Kea service and configured DHCP functionality
- DNS service
- WireGuard interfaces/handshakes where enabled
- XDP attachment/functionality where enabled
- management listener
- critical FR OS services

Avoid making general Internet reachability a required invariant; the router may legitimately be offline during a kernel upgrade.

The key principle should be:

> A kernel is healthy only if the configured FR OS dataplane and control plane are healthy.

## FR-NEW-004 — XDP SNI enforcement can be bypassed by out-of-order TCP segmentation

**Severity:** Medium  
**Category:** Security enforcement completeness  
**File:** `bpf/xdp_sni_filter.c`

### Description

The current XDP SNI tracking logic expects TCP segments to arrive in the sequence it is tracking.

The flow follower uses the expected next sequence number and stops following when a segment does not match the expected sequence.

This is reasonable for a lightweight high-speed parser, but it creates an enforcement gap when TCP segments arrive out of order.

### Failure scenario

A TLS ClientHello is split across two TCP segments:

- Segment A arrives first and establishes tracking.
- Segment B contains the SNI value that should be blocked.
- Segment B arrives before A, or otherwise does not match the currently expected sequence.
- The follower stops following the flow.
- Segment B is allowed through the XDP policy path.
- The kernel TCP stack later buffers/reorders the segments.
- A and B are reassembled and the destination receives the complete ClientHello.

The blocked SNI therefore reaches the connection despite the XDP SNI policy.

### Important distinction

This is **not** primarily a memory-safety or eBPF verifier issue in the reviewed implementation.

The current parser's boundary handling is materially improved compared with the earlier revision.

This finding is about **policy completeness**.

### Recommendation

Choose and document one of these models:

**Option A — Best-effort classification**

Explicitly state that XDP SNI filtering is an optimization/best-effort enforcement layer and is not a security boundary.

**Option B — Fail closed for tracked flows**

For an already tracked flow, unexpected sequence numbers should not silently transition to an untracked/pass state. The flow can be terminated/quarantined/held according to the policy model.

**Option C — Full TCP reassembly**

Implement real TCP stream reassembly.

This is considerably more expensive and complex and is probably inappropriate for the first high-speed implementation.

For FR OS, **Option B is the practical security-oriented design** if the feature is advertised as enforcement rather than merely classification.

## FR-NEW-005 — Managed static IP deletion is not reconciled

**Severity:** Medium  
**Category:** Network configuration correctness  
**File:** `src/frfw/ifaddr.py`

### Description

The interface-address application path uses address replacement semantics to establish desired addresses, but does not appear to maintain a dedicated inventory of addresses previously managed by FR OS and remove addresses that are subsequently deleted from configuration.

This creates possible state drift between:

- FR OS configuration
- kernel interface state

### Failure scenario

Initial configuration:

```text
192.168.1.1/24
```

Configuration is later changed to:

```text
10.0.0.1/24
```

The desired new address is applied, but the old managed address can remain present on the interface.

Possible consequences include:

- unexpected management reachability
- routing ambiguity
- source-address selection changes
- firewall rules matching an address that should no longer exist
- difficult-to-reproduce configuration drift

### Recommendation

Maintain explicit FR OS-managed network state.

On apply:

1. determine the desired address set;
2. determine the previously FR OS-managed address set;
3. calculate additions/changes/deletions;
4. apply additions;
5. remove obsolete addresses that FR OS itself owns;
6. verify final state.

Do **not** blindly remove every address on an interface because operators may intentionally have non-FR-OS-managed addresses.

## FR-NEW-006 — Provisioning is still not a true cross-subsystem transaction

**Severity:** Medium  
**Category:** Correctness / availability / configuration consistency  
**File:** `src/frfw/provision.py`

### Description

The current implementation has improved handling for firewall runtime security state, but configuration application still spans multiple independently mutable subsystems.

A complete provisioning operation can touch:

- nftables
- interfaces
- VLANs
- forwarding
- Kea
- DNS
- WireGuard
- XDP
- management listeners
- PQC configuration
- SSH
- WebUI state

These operations cannot all be committed atomically by the underlying subsystems.

### Failure scenario

For example:

1. nftables is successfully applied.
2. Interface changes are successfully applied.
3. Kea is successfully reconfigured.
4. WireGuard or management configuration fails.
5. The operation reports failure.
6. The machine is left with a mixture of old and new state.

The result can be a router that is neither the previous known-good configuration nor the newly requested configuration.

### Recommendation

Move toward an explicit state machine:

```text
CONFIG
  |
PRE-FLIGHT
  |
STAGE
  |
VERIFY ALL
  |
COMMIT
  |
HEALTH CHECK
  |
CONFIRM
```

The key requirement is that failure after partial commit must have a deterministic recovery path.

Where true atomicity is impossible, use:

- snapshots of FR OS-owned state
- deterministic rollback
- post-commit health checks
- a persistent transaction journal
- explicit last-known-good configuration
- recovery/boot-time reconciliation

This finding is an evolution of the earlier provisioning-transaction finding; the previous specific runtime firewall-state-loss problem is substantially improved in this revision.

## FR-NEW-007 — Minimum administrator password length is only 8 characters

**Severity:** Low  
**Category:** Authentication hardening  
**File:** `src/frfw/passwords.py`

### Description

The password policy defines:

```text
MIN_LENGTH = 8
```

The surrounding authentication design is otherwise strong. The reviewed implementation includes modern password hashing with scrypt, legacy PBKDF2 upgrade handling, common-password blocking, username checks, repetitive-password checks, MFA support and login throttling.

The issue is therefore not that the password subsystem is weak overall; rather, the minimum length is conservative for a modern internet-facing router administration account.

### Recommendation

Increase the minimum to at least 12 characters, or use a passphrase-oriented policy.

Do not impose unnecessary composition rules that reduce password-manager usability.

A sensible policy is:

- minimum 12 characters
- allow substantially longer passwords
- allow spaces/passphrases
- retain breached/common-password rejection
- retain MFA
- retain throttling

# 3. Previously identified issues that are materially improved or fixed

The following earlier findings were specifically re-checked and should **not** simply be carried forward unchanged.

## Dependency supply chain

The Python dependency installation path is substantially hardened compared with the earlier revision.

The reviewed implementation uses a lock/hashing strategy with exact versions and hash verification rather than relying on unconstrained root-level PyPI resolution.

There is still some stale/contradictory documentation in `docs/RELEASING.md` that should be cleaned up so the documented release process exactly matches the enforced one, but the earlier runtime supply-chain finding is materially addressed.

## Debian security updates

The earlier concern that Debian security updates were explicitly disabled is no longer applicable in the same form.

The current installer/update flow includes explicit handling for Debian security updates.

## Runtime firewall security state

The earlier failure mode where a successful firewall apply could inadvertently discard runtime security enforcement state has been materially improved.

The current ruleset generation integrates runtime security state more safely.

This should still receive regression tests because it is a security-critical invariant.

## CSRF protection

Explicit CSRF protection is now present.

The previous finding that there was no dedicated CSRF-token mechanism is therefore no longer valid.

## Release public key

A production release public key is now present:

`src/frfw/release_keys/fros-release-1.pem`

This addresses the earlier observation that the reviewed revision lacked the release public key.

The private-key/CI trust-boundary issue remains separately important and is covered by FR-NEW-002.

## XDP memory-safety boundary

The earlier XDP parser concern around using only `data_end` without sufficient protocol-derived bounds has been materially improved.

The current implementation distinguishes the eBPF verifier's packet boundary from protocol-derived parsing limits.

The principal current XDP concern is therefore enforcement completeness, especially TCP ordering/reassembly, rather than an obvious out-of-bounds read.

## Authentication/password storage

The password implementation is significantly stronger:

- scrypt password hashing
- controlled parameters
- PBKDF2 legacy upgrade
- common-password rejection
- username checks
- repetitive-password checks
- MFA
- throttling

No authentication bypass was identified in this review.

# 4. Positive security observations

The following areas were reviewed positively:

### WebUI authentication and authorization

The WebUI authentication/session/RBAC architecture is substantially mature.

No confirmed authentication bypass or straightforward privilege-escalation path was identified during this review.

### Privileged helper boundary

The privileged helper uses a Unix-domain socket with peer-credential checking and command/input allowlisting.

No direct arbitrary-root-command execution path was identified in the reviewed code.

This is an important architectural boundary and should be preserved.

### nftables default-deny posture

The firewall architecture maintains a strong default-deny orientation and separates generated policy from privileged application.

This is preferable to dynamically constructing shell commands from WebUI input.

### Signed update architecture

The existence of a release public key and signature-verification path is a strong foundation.

The remaining problem is not the concept of signed updates; it is ensuring that the **correct source commit** is what gets signed and that the signing key cannot be reached by an untrusted/mutable build path.

### Kernel trial/fallback concept

The kernel update design itself is a strong feature.

A staged kernel, trial boot, health confirmation and automatic fallback is substantially safer than replacing the active kernel without rollback.

The main remaining issue is making the health contract representative of an actual functioning router.

### Configuration validation

The project makes meaningful use of typed/configuration validation rather than treating arbitrary YAML as executable configuration.

### Security architecture direction

The overall architecture is moving in the right direction:

```text
Untrusted WebUI
      |
      v
validated configuration
      |
      v
controlled privileged boundary
      |
      +---- nftables
      +---- network state
      +---- WireGuard
      +---- DHCP/DNS
      +---- XDP/eBPF
```

That separation is substantially preferable to giving the WebUI direct root shell access.

# 5. Recommended remediation priority

## Priority 0 — Release trust chain

Address **FR-NEW-001** and **FR-NEW-002** before treating the release system as production-grade.

The most important architectural objective is:

> No mutable CI path should be able to silently choose what source code becomes a trusted, signed FR OS release.

The desired chain is:

```text
immutable release tag
        |
        v
exact commit SHA
        |
        v
reproducible/controlled build
        |
        v
artifact digest
        |
        v
protected signing operation
        |
        v
signed release
        |
        v
router signature verification
```

## Priority 1 — Router survivability

Address **FR-NEW-003** and **FR-NEW-006**.

A firewall/router OS needs deterministic behavior when a subsystem fails during an update or configuration transaction.

## Priority 2 — Enforcement semantics

Address **FR-NEW-004**.

The project should explicitly define whether XDP SNI filtering is:

- a best-effort optimization, or
- a security enforcement boundary.

The implementation and documentation must agree.

## Priority 3 — State reconciliation

Address **FR-NEW-005**.

Persistent network configuration should converge deterministically to the configured state.

## Priority 4 — Authentication hardening

Address **FR-NEW-007**.

This is low-risk relative to the release and provisioning findings.

# 6. Recommended regression tests

The following tests would materially reduce the chance of regressions.

### Release tests

- release tag points to commit A, workflow executes against commit B -> **must fail**
- release tag is moved -> **must fail unless explicitly authorized**
- release artifact metadata contains exact source commit SHA
- signing job cannot access private signing key from ordinary build job
- untrusted workflow/action cannot invoke production signing

### Kernel tests

- new kernel boots but WAN driver fails -> trial must fail
- LAN driver fails -> trial must fail
- nftables fails -> trial must fail
- Kea fails -> trial must fail
- WireGuard fails when configured -> trial must fail
- XDP fails when configured -> trial must fail
- management listener fails -> trial must fail
- all configured services healthy -> trial may be confirmed

### Network reconciliation tests

- remove an FR OS-managed static address -> address disappears
- replace a prefix -> old address disappears
- preserve explicitly unmanaged address -> address remains

### Provisioning tests

Inject failure after each major subsystem and verify:

- transaction is marked failed
- persistent transaction state records the failure
- last-known-good configuration remains recoverable
- no subsystem is silently left in an undocumented intermediate state

### XDP tests

Test:

- normal in-order TLS ClientHello
- ClientHello split at every relevant boundary
- out-of-order TCP segments
- retransmissions
- duplicate segments
- overlapping segments
- missing segments
- FIN/RST
- IPv4 fragmentation
- IPv6 traffic
- TLS 1.3 ClientHello variations

The expected policy behavior should be explicitly asserted for each case.

# 7. Overall assessment

**FR OS at `3aec35f` is substantially more mature than the earlier reviewed revision.**

The most important improvement is that the security architecture is no longer dominated by basic WebUI/root-helper concerns. Authentication, privileged execution boundaries, dependency handling, firewall-state handling, release-key presence and XDP parser safety have all moved in the right direction.

The risk profile has shifted toward the areas that become critical as FR OS approaches a real distributable product:

1. **Can the build system prove exactly what source code was signed?**
2. **Can the release signing key be isolated from ordinary CI execution?**
3. **Can a failed kernel/configuration transition recover deterministically?**
4. **Do high-speed enforcement mechanisms provide the security semantics their users expect?**
5. **Does runtime state always converge exactly to declared configuration?**

The two High findings are therefore concentrated in the **software supply chain and release trust model**, not in the normal WebUI request path.

### Final rating

**Security posture: Good architectural foundation, not yet production-release hardened.**

The recommended next milestone is not a broad rewrite. It is to harden the **release trust chain**, strengthen **kernel/configuration transactional safety**, and define the exact **security semantics of XDP enforcement**.
