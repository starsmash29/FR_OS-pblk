## High

### C-01 — Quarantine does not cut a quarantined host off
`build_ruleset` puts `ip saddr @ids_quarantine drop` only in `chain input` (`builder.py:173`); `chain forward` (`builder.py:217`ff) never references the set. Checked by rendering `examples/config.yaml`: the only `@ids_quarantine` line is in `input`.

The AI IDS scores the *sources of conntrack flows* (`ai_ids/daemon.py:207`) — overwhelmingly LAN clients talking to the internet — and the TLS-fingerprint feature "blocks and quarantines" devices the same way.

**Scenario:** a LAN machine is infected and starts scanning/beaconing; the IDS flags it and the dashboard shows it quarantined. Its forwarded traffic (internet, other zones) is untouched; only its packets to the router itself are dropped. The IPS action does not do what the UI and README say.

**Fix:** add `ip saddr @ids_quarantine drop` (and `ip daddr @ids_quarantine drop` for inbound port-forwards) at the top of `chain forward`, ahead of `ct state established,related accept` so open sessions are cut too. Add a netns test like the IoT-isolation one: a quarantined client can no longer reach a host through the router.

### C-02 — No Debian security updates, at build time or on the device
`--security false` (`auto/config:160`) was a workaround for an old live-build that used the wrong security suite path. So the ISO is built without `bookworm-security`. There is also no on-device path: no `unattended-upgrades`, and the FR_OS updater only `pip install`s the frfw package. Kernel, OpenSSL, OpenSSH, dnsmasq, Kea and nftables therefore stay at their build-time versions for the life of an installation.

**Fix:** add `bookworm-security` explicitly (a `config/archives/*.list.chroot` entry, or re-enable `--security` with the correct `bookworm-security` suite) and fail the build if `apt-cache policy` doesn't show it. Then decide the device policy: unattended security upgrades from the security suite, or a rule that each Debian security release triggers a new FR_OS image and release. Document whichever is chosen in SECURITY.md.

## Medium

### C-03 — Runtime security state across an apply
Every apply starts with `flush ruleset`. `apply_all` snapshots the brute-force jail, IDS quarantine, ZTNA sessions and IoT isolation first, then re-adds them *after* the new ruleset is loaded (`provision.py:157-173`).
- Between the load and the re-adds, every jailed/quarantined host is briefly allowed.
- `restore_after_reload` swallows every per-element error (`ids_quarantine.py:106-122`, same pattern in the others).
- The result message reports `len(snapshot)` as "preserved", not what was actually restored, so a failed restore is reported as success.

**Fix:** render the live elements (with their remaining timeouts) into the same nft script, so the flush and the restore are one atomic transaction. At minimum, count the restores that actually succeeded and fail or warn loudly on a shortfall.

### C-04 — No guardrails on quarantine targets or duration
`quarantine_ip` is a sensor-role command (`peer.py:43`). The helper accepts any IPv4 address and any positive duration (`server.py:241`). The drop rule sits *above* `iifname "lo" accept` and `ct state established,related accept`.

The IDS has no built-in exemptions beyond `ai_ids.excluded_macs`. It scores every conntrack source, including the router's own outbound connections and inbound flows through port forwards.

**Scenarios:**
- (a) A compromised parser daemon quarantines the admin's workstation, the upstream gateway or 1.1.1.1 for years. The router then loses its DNS, NTP and update traffic, or the admin loses the webUI.
- (b) Needs verification: spoofed-source SYNs to a port-forwarded service make remote addresses look "anomalous", and the IDS quarantines them.

**Fix:**
- In the helper: refuse loopback, the router's own addresses, the configured gateway and DNS servers, and management-zone addresses of current admin sessions; cap the duration (e.g. 24 h).
- In the engine: only score sources from internal zones.

### C-05 — SNI filtering bypassed by QUIC
The XDP program only parses IPv4 TCP to port 443 (`xdp_sni_filter.c:843`), and the ruleset has no rule for UDP/443. Browsers use HTTP/3 (QUIC over UDP/443) with most large sites, so a domain on the SNI blocklist — or an app blocked with `app_control.block_via_xdp` — stays reachable with no user action. ECH is documented in the C header as a known gap; QUIC is not documented anywhere.

**Fix:** when the SNI filter or XDP app blocking is on, `reject` UDP/443 forwarded from the filtered zones so clients fall back to TCP/TLS (where the SNI is visible). State the remaining gaps (ECH, IPv6) on the XDP screen.

### C-06 — Unpinned dependencies installed as root (same as FR-001)
Both the image hook and `_install_release_dir` run `pip3 install … [webui]` as root against PyPI with `>=` ranges. pip's build isolation also fetches the build backend (setuptools) from PyPI at install time. A signed FR_OS release therefore does not pin what code actually lands on the router.

**Fix:** ship a hash-locked `requirements.lock` and install with `--require-hashes --no-build-isolation` from wheels bundled in the signed release tarball, so an update needs no PyPI at all.

## Low

### C-07 — `/metrics` without a token (extends FR-007)
Besides the information exposure FR-007 describes, each request makes the root helper run several `nft -j list set` calls and other status work. Any LAN client can do this in a loop, unauthenticated.

**Fix:** generate a token on first boot so the endpoint is protected by default, and cache the helper-backed values for a few seconds.

### C-08 — Parser daemons can read secrets in config.yaml
`fr-ai-ids`, `fr-appid` and `fr-iot-scan` run with `SupplementaryGroups=fr_os-webui`, so they can read `config.yaml` (0640 root:fr_os-webui). That file holds ZTNA users' PBKDF2 hashes and the metrics token digest. A parser bug therefore leaks crackable credentials.

**Fix:** give the sensors a root-written, secrets-free copy of the config they need, and drop the `fr_os-webui` group.

### C-09 — Downgrade through the update helper
`apply_update` only refuses `target == current` (`update.py:562`). Any older signed release can be installed through the `apply` command, bringing back vulnerabilities that were fixed. The update helper only serves root and the webUI's account, so this matters after a webUI compromise or for a mistaken admin action.

**Fix:** refuse `target < current` in `apply`. Going back stays possible through `rollback`, which is explicit and one level deep.

### C-10 — Unbounded log streams
`GET /xdp/logs/stream` needs only `require_login`, so viewers can use it too. Each request spawns `journalctl -f` with no per-user or global limit. After the client disconnects, the process lingers until the next journal line arrives.

**Fix:** allow one stream per session with a small global cap, and terminate the process on disconnect.

### C-11 — No security headers
There is no CSP, `frame-ancestors`/`X-Frame-Options` or `Referrer-Policy`. The session cookie is `SameSite=Lax`, so a cross-site frame is not logged in, and the practical clickjacking/CSRF risk is low (this also covers FR-011's concern). The headers are cheap defense in depth: `default-src 'self'` works because every asset is served from `/static`.

## Positive observations
- Peer-uid–based command policy on both helper sockets.
- Signed-release verification with the version bound into the signed checksum file.
- Tarball path-traversal checks.
- SSH hardening (`PermitRootLogin no`, `PasswordAuthentication no`).
- Server-side session store with revocation.
- Argon/PBKDF2-style hashing with lockout.
- MFA.
- A viewer RBAC enforced in one dependency and tested over every route.
- Management ports dropped from non-management zones ahead of admin rules.
- Fail-closed baseline ruleset.
- Systemd sandboxing on every unit.
